# Privacy implementation boundary — 0.5.0

The consumer-facing promise is: **Your data stays on this computer. This app does not send or automatically save it.** Imports and exports are explicit each session. This document explains the application boundary behind that promise.

## Runtime data access

- `MainWindow.Import_Click`: an explicit native file picker selects local files. A `StreamReader` reads only those selected files. There is no folder scan, file watcher, startup data loading, or retained recent-file list. CSV decoding/parser errors appear in the UI.
- `Core.cs`, `SchemaNaming.cs`: raw working values, source paths, joins, pivots, provenance, and validation are ordinary in-memory objects. Matching supports ID, one optional additional matching column (such as person/role), and one optional time/grouping column. Recommendations use deterministic column-name, completeness, uniqueness, and cross-file matching checks. Repeated-column suggestions use local names and metadata. No model, database, filesystem, or network engine is involved.
- Compound matching: an ID-only source applies its values to all observed roles/times for that ID; an ID/time source without an additional key applies values to all roles only at the matching time. Role-specific values remain scoped to their full configured key. Another role's follow-up does not create phantom records for a missing role. Wide output remains one row per ID, using role/time-qualified columns only for source-observed roles; selected genuine missing values remain represented. Duplicate full keys and missing selected keys stop matching rather than multiplying or silently discarding records. All of these checks use current in-memory objects.
- `RefreshPreview`: a snapshot is transformed in a worker task, then bound to an in-memory DataTable. The grid virtualizes its visual rows/columns; it does not persist them.
- `Presentation.cs`: sort priorities, column positions, custom row-variable choices, and output-name overrides are held only in memory, separately for each layout. Stable variable identities and source-cell provenance preserve correct edits after rearranging or sorting. Exports use the preferences for each selected shape and apply its typed filters plus the current text search. The purple palette is fixed and there is no color-setting persistence.
- `Diagnostics.cs` / `MatchReview.cs`: matching diagnostics compute complete/missing/duplicate ID/additional/time key counts and exact ID coverage from current in-memory source objects. The issue list retains source-record provenance for inspection; it does not export, log, remove, or repair those records automatically. Jumping to a source record explicitly clears search/filter preferences so it can be displayed. No participant files are scanned to populate the review.
- `MappingSchema.cs` / `MappingEditor.cs`: batch column mappings and Keep choices are staged as separate in-memory metadata until Apply. Validation and the before/after preview use the current source already in memory. Cancel drops the staged choices. Applying mappings changes the working metadata, not original CSV values or files.
- Missing-value policy: file defaults and optional per-variable exact-code overrides stay in memory. Variables can inherit defaults or use independent rules; changing an override does not rewrite stored source text. The rule dialog and type-conversion preview compute affected/missing/invalid counts and representative before/after values locally. Each recorded conversion captures its effective per-variable rules for replay. Literal NA/NULL/dot text is not automatically reclassified. R bundle readers use a collision-free token to distinguish missing values from literal text and true empty Text. SAS character blanks cannot distinguish empty strings from character missing. These rules do not modify imported original files.
- `Filtering.cs` / `FilterControls.cs`: typed AND/OR rules and case-insensitive Search rows text are session-only preferences. They are evaluated locally against stable output fields and passed to explicitly requested R/SAS code generation. Missing or incompatible rule variables block the operation rather than silently dropping a rule for a different export shape. The rule builder's draft preview does not write data or execute external programs.
- `HoverActions.cs`: delayed action menus are generated from the same in-memory actions as right-click menus. Hovering does not write previews, preferences, or data.
- Original snapshots and cleaning history: original rows are captured in memory at import/example creation. Cell edits, exact recodes, and conversions append typed in-memory steps. Session copies preserve these steps for undo/redo. A generator replay check catches unrecorded mutations; no automatic recipe/session files are created.
- `SessionHistory.cs`: a visible history lists actions and up to 50 before/after value or metadata examples per data change. Those examples may themselves contain sensitive working values, but remain only in process memory. View/filter/navigation activities are distinguished from data actions. Undo/Redo covers up to 12 in-memory data snapshots; view preferences are changed through their controls. No history, recovery, recipe, or session file is automatically saved. Clear and close discard original/working sources, histories, and presentation preferences. Managed strings and freed heap regions are not securely wiped.
- `Export.cs`, `ExportReview.cs`, and `ExportReviewWindow.cs`: export options prepare each selected shape in memory, then show counts, names, included files, actual missing-value codes, and up to eight sample rows. Reviewing or cancelling does not write files. Only proceeding through Choose destination and confirming the native Save dialog writes the selected export. Wide and Long can be exported together into separate ZIP subfolders; choosing an export shape does not alter the preview layout. ZIP entry contents are prepared in memory before opening the chosen destination, with no intermediate dataset files. Dataset exports contain selected values and source names in their dictionary, but no source file paths or recorded cleaning history.
- `Recipe.cs`, `CodeModel.cs`, `RCode.cs` and `SasRecipe.cs` generate code entirely locally from in-memory metadata and recorded steps. The application never executes R or SAS, launches a statistical process, or asks a model to inspect data. Code previews can contain local input paths and the values explicitly changed/replaced. Unchanged datasets are not embedded in code.
- `CodeWindow.cs`: explicit Save code writes one chosen `.R` / `.sas` file; explicit Copy writes the chosen code to the clipboard. The fictional-example ZIP action explicitly writes original built-in example CSVs and scripts. Imported originals cannot be copied by that action. No previews or recipes are saved automatically.
- Import/export dialogs may cause Windows to retain path metadata under its own policies. Windows paging/crash dumps, local malware, clipboard sync, and cloud-synced folders are outside this application's process boundary.

## Network and dependencies

There are no network namespaces/calls, external packages, web views, external process launches, model clients, remote assets, extension loaders, update checks, telemetry endpoints, or online execution paths in the application source. It uses the installed Microsoft .NET/WPF runtime. Building requires a local .NET SDK; the provided build configuration has no external package sources and opts out of .NET CLI telemetry.

This statement describes the application's code. It does not assert that Windows or other applications on the device never contact a network. No institution-specific compliance certification is asserted.

## Development practices

- Use synthetic examples only. The sixth household example is generated fictional data with ID-only details, long role/time questionnaires, and wide role-specific scores. The `--synthetic-check --compound-example` development window opens that built-in fixture with real-file imports disabled. Real participant files were not accessed while developing this prototype.
- Keep builds, caches and test fixtures inside the ignored `output/` and `work/` folders.
- Do not include datasets, exports, local absolute paths, secrets, or error dumps in GitHub commits.
- Reproducible code export is explicitly user-requested. Keep it behind Save/Copy actions and show that code can include identifying corrections or paths. Do not add automatic recovery, persisted sessions, or real-source bundles.
- Reject lossy transformations and invalid conversion values visibly, without logging dataset content.
- Runtime debug symbols are development artifacts; the distribution ZIP omits them.

## Validation scope

The verification harness covers CSV edge cases, matching diagnostics, staged repeated-column mappings, per-variable missing policies and conversion previews, typed filters, export review, ID/additional/time labels, safe matching/stacking, role-scoped follow-up schedules, ID-only context broadcast, one-ID wide output, layouts, sorting/dragging, provenance, original/history isolation, explicit exports, and cleaning-code replay. Native runtime checks use fictional original inputs and compare generated-program output with application output. UI checks use fictional-only verification windows with imports disabled. Release-specific R/SAS runtime results and remaining limitations are recorded in the changelog rather than being a privacy guarantee.

The local SAS executable was found, but isolated batch initialization exited 115 before producing the requested log or test output. No cause was established and no generated-program correctness is claimed from that attempt. It used an explicit installed configuration and task-only input/autoexec/WORK/SASUSER/output paths; personal SAS sessions, user AppData, and real datasets were not inspected. The WideLong application itself does not launch SAS. An independent security review remains separate from functional verification.
